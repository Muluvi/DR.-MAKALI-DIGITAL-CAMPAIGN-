# Site outline — Kitui 2027 Strategy Portal

Every heading the site renders, in render order, with its file, its heading level,
its anchor id and its section number. Strings are reproduced exactly as they appear
in source: nothing here is summarised, renamed or re-cased.

Generated by reading `public/content/*.md` and `components/**`, and by re-running the
repo's own derivation rules — `headingNumber` / `headingSlug` / `sectionId`
(`lib/heading-slug.ts`), `buildSectionIndex` (`lib/section-index.ts`) and
`segmentContent` (`lib/collapse-groups.ts`) — against the current content. It is
therefore a reading of the code, not of a deployment.

## How to read this

**Anchor ids are derived, never authored.** `MarkdownViewer` overrides `h2` and `h3`
only. For each, it runs `headingSlug(text)`, which returns the heading's leading
section number with dots replaced by dashes, and mints `` `<tabId>-sec-<slug>` ``.
Everything follows from that:

- an `h2`/`h3` with a leading number gets an anchor, and the anchor can never
  disagree with the number — the number *is* the anchor;
- an `h2`/`h3` **without** a leading number gets `id={undefined}` and no copy-link
  button (`SectionHeading` takes `id: string | null`);
- `h1`, `h4` and `h5` are not overridden at all, so they never get an anchor,
  whatever they are numbered.

**The tab prefix is the part that can disagree.** `tabId` comes from the file the
heading is in, and the leading digit of the section number comes from the document's
older §0–§9 spine. The five-part restructure moved sub-sections between files without
renumbering them, so the two now disagree in six places. Those are listed in
[Flag 1](#flag-1--section-numbers-split-across-files).

**Two numbering systems.** The reader navigates 1, 2, 3, 4A–4E, 5 (`SECTIONS` in
`lib/heading-slug.ts`). The prose numbers itself §0–§9. Nothing on the page
reconciles them; this table's first two columns are the mapping.

**Rendered-as column.** `SectionHeading` = the anchored heading component.
*disclosure panel of §N* = the heading is not rendered as a heading at all; it is the
label on a `DisclosureGroup` accordion button, because `segmentContent` found two or
more sibling `h4`/`h5` under a 150-word-plus parent. *+ ProseFold* = the parent
section's body after its opening paragraph is behind a "read more". *⚠︎unresolved* =
the panel body contains an `[Insert …]`, `[Confirm …]` or `Not yet`, which the closed
label flags.

**`↳` rows** are components mounted immediately after a heading by
`HEADING_INSERTS` in `components/MarkdownViewer.tsx`. Their eyebrow labels and card
titles are quoted where the component has literal ones. All 39 keys resolve to a
heading that exists (21 `h2`, 18 `h3`).

## Flag 3 — `headingNumber` reads list numbering as section numbering

`LEADING_NUMBER` is `/^(\d+(?:\.\d+)*)\.?\s/`, which matches `1. ` as readily as
`1.2.3 `. Twenty-three headings written as numbered list items are therefore assigned
a bare section number:

- the eight constituency `h5`s (`1. Mwingi North Constituency …` → §1 … `8. Kitui South Constituency …` → §8), `2-evidence.md:245–293`
- the six voter segments under §2.4.1 (`1. The Rural Agrarian & Smallholder Baseline` → §1 …), `2-evidence.md:1057–1129`
- the four field channels under §4.1.3, `4b-ground.md:121–143`
- the five stack components under §6.3.1, `4d-technology.md:290–332`

All are `h4`/`h5`, so `MarkdownViewer` never asks for a slug and no bad anchor is
minted. `buildSectionIndex` reads `h2`/`h3` only, so none reaches the index either.
The exposure is latent: promoting any of them to `h3` would mint `evidence-sec-1`,
`ground-sec-1`, `technology-sec-1` and so on, and `SectionNumberMap` would then map
the bare number `"1"` to whichever file `SECTIONS` lists last.

## Flag 4 — `NEVER_COLLAPSE` does not protect the section it names

`lib/collapse-groups.ts` declares `NEVER_COLLAPSE = new Set(["9.2"])`, with a comment
explaining that choosing a service level means holding the ceiling and the levels side
by side, and that an accordion shows one at a time.

The guard is tested per heading, against that heading's own number. The three levels
are `h4`s under `### 9.2.5 The three service levels`, whose number is `"9.2.5"` — not
`"9.2"` — so the guard does not fire, and `segmentContent` returns:

```
group  "9.2.5 The three service levels"
       panels: Level 1 — LEAN | Level 2 — STANDARD (recommended) | Level 3 — PREMIUM
```

The three service levels are behind three separate taps, one visible at a time. `## 9.2
Service levels` does match the guard, but its body is empty — the next heading is
`### 9.2.5` two lines later — so the entry protects nothing. Matching on prefix
(`9.2` covering `9.2.5`) would restore the documented intent.

## Flag 6 — no table has a caption

# What is sound

Recorded because each was checked and each holds:

- **All 39 `HEADING_INSERTS` keys resolve** to a heading that exists in the current
  content — 21 `h2`, 18 `h3`. The map's own comment claims this; it is true.
- **All 165 in-prose `Section N.N` references resolve** to a heading that carries that
  number. None is orphaned.
- **No two headings claim the same section number**, so `SectionNumberMap`'s
  number → id map has no silent last-one-wins collision.
- **No `h3` is orphaned**: every `h3`'s parent `h2` number exists somewhere in the
  document (six of them in another file — Flag 1).
- **Every `h2`/`h3` has an anchor.** There is no numbered sub-section above `h4` that
  a link cannot reach.
- **Numbering gaps are deliberate, not dangling.** §9.2 runs 9.2.5, 9.2.6; §6.6 runs
  6.6.2, 6.6.3; §3 skips 3.3. Nothing references the missing numbers.
